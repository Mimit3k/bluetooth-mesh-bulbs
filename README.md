# Mesh Bulbs — computer control for LEDVANCE SMART+ BLE Mesh lamps

Control Bluetooth **SIG Mesh** lamps (tested target: LEDVANCE/Sylvania SMART+
A19 60 W, model `60A19CBLE`, item `75741SYL`) directly from a Linux or
Windows computer.

- No LEDVANCE app, no account, no cloud, no hub.
- No root/admin, no Docker, no vendor cloud.
- On Linux: no BlueZ `bluetooth-meshd` (Ubuntu's BlueZ 5.85 ships without it).
- Pure Python: `btmesh` (mesh crypto, provisioning, proxy) over `bleak`.
- Desktop GUI (PyQt6) **and** a scriptable CLI.

## What's in here

| Path | What it is |
|---|---|
| `bulbgui.py` | PyQt6 desktop app: bulb list, dimmer, colour, add-bulb wizard |
| `bulbctl.py` | CLI for scripts and quick commands |
| `meshcore.py` | shared state, discovery, provisioning and persistent BLE links |
| `src/btmesh/` | vendored `btmesh` library (MIT) |
| `phase0/` | upstream harness; `provision_and_toggle.py` does PB-GATT provisioning |
| `tests/` | offline regression suites (no Bluetooth hardware needed) |
| `bulbgui`, `bulbctl` | Linux launchers that use `.venv/bin/python` |
| `bulbgui.cmd`, `bulbctl.cmd` | Windows launchers that use `.venv\Scripts\python.exe` |
| `setup-linux.sh`, `setup-windows.ps1` | environment setup |
| `requirements*.txt` | runtime and development dependencies |
| `packaging/bulbgui.desktop.in` | desktop-entry template installed by `setup-linux.sh` |
| `icon.svg`, `icon.ico` | Linux and Windows icons |
| `third_party/` | upstream metadata and licence provenance for the vendored code |
| `.venv/` | generated by the setup script; never committed |

## Linux one-time setup

You need 64-bit Python 3.12 or newer with the `venv` module, BlueZ, and a
working Bluetooth adapter. On Debian/Ubuntu, install `python3`, `python3-venv`
and `bluez` if they are missing.

```bash
git clone https://github.com/Mimit3k/bluetooth-mesh-bulbs.git
cd bluetooth-mesh-bulbs
./setup-linux.sh
```

The script creates `.venv`, installs the dependencies, and adds **Mesh Bulbs**
to the application menu. It uses [`uv`](https://docs.astral.sh/uv/) if it is
already installed (some distributions ship Python without `ensurepip`), and
falls back to `python -m venv` otherwise. To skip the menu entry:

```bash
INSTALL_DESKTOP=0 ./setup-linux.sh
```

If `python3` is older than 3.12 while a newer version is installed alongside
it, point the script at it: `PYTHON=/usr/bin/python3.15 ./setup-linux.sh`.

If Bluetooth is soft-blocked, unblock it once:

```bash
sudo rfkill unblock bluetooth
```

To run from the checkout without the menu entry:

```bash
./bulbgui        # desktop app
./bulbctl devices
```

## Windows 10/11

The same GUI, CLI and mesh keys work on Windows. Bluetooth goes through the
Windows WinRT stack via `bleak`, so there is no BlueZ or `bluetooth-meshd`
requirement. No administrator rights are needed.

You need 64-bit Windows 10/11 with a working Bluetooth adapter and a 64-bit
CPython **3.12 or newer** from
[python.org](https://www.python.org/downloads/windows/) (tick **Add python.exe
to PATH** during installation). Python 3.15 is accepted; there is no
hard-coded version list.

The setup script finds every registered 64-bit Python 3.12+ (through the `py`
launcher, `python`/`python3` on PATH, the standard install folders, and
uv-managed installs) and picks the newest. If the newest release has no PyQt6
wheel yet, pin a version that does, or pass an interpreter explicitly:

```powershell
.\setup-windows.ps1 -PythonVersion 3.13
.\setup-windows.ps1 -Python "C:\Path\To\python.exe"
```

1. Clone the repository (or download the ZIP from GitHub and extract it) on
   the Windows computer, for example `C:\Users\you\bluetooth-mesh-bulbs`. **Do not copy
   `.venv/` from Linux**: that environment is Linux-specific and the setup
   script builds a Windows one.
2. Open PowerShell in that folder and run:

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\setup-windows.ps1
   ```

   This creates `.venv\` and installs the dependencies into it. Nothing is
   installed system-wide. If an existing `.venv` is present, setup asks whether
   to remove it and create a fresh one; answer **Y** after changing Python
   versions or updating dependencies, or **N** to reuse it. If Python is
   somewhere unusual, pass it explicitly:
   `.\setup-windows.ps1 -Python "C:\Path\To\python.exe"`.
3. If the lamp is already provisioned (for example by the Linux computer), move
   the mesh configuration to Windows. On the old computer choose
   **Export… → Whole mesh** in the GUI, or run
   `./bulbctl export --all mesh-backup.json`, then transfer that file. On
   Windows choose **Import…** in the GUI, or run
   `.\bulbctl.cmd import mesh-backup.json`. A single bulb can be moved with
   **Export… → Selected bulb** / `export --device NAME`.

   Alternatively, copy `state.json` directly (`~/.config/bulbctl/state.json` on
   Linux, with the app closed) into
   `%LOCALAPPDATA%\bulbctl\state.json` on Windows:

   ```powershell
   New-Item -ItemType Directory -Force "$env:LOCALAPPDATA\bulbctl" | Out-Null
   Copy-Item .\state.json "$env:LOCALAPPDATA\bulbctl\state.json"
   ```

   Copy only `state.json`; don't copy `state.json.lock` (it belongs to a running
   process) or the `.tmp` file. Export/import is preferred because it validates
   the file and creates it with private permissions.
4. Start the app with `.\bulbgui.cmd` (double-clicking it also works), or use
   the CLI via `.\bulbctl.cmd`.

Keep `bulbgui.cmd`, `bulbctl.cmd` and `.venv\` together; the launchers resolve
everything relative to themselves. `bulbgui.cmd` uses `pythonw.exe`, so no
console window appears. To see startup errors, run
`.venv\Scripts\python.exe bulbgui.py` from PowerShell.

For a desktop or Start-menu shortcut, point it at `bulbgui.cmd` and choose
`icon.ico` as its icon.

The Windows state path is `%LOCALAPPDATA%\bulbctl\state.json`. Windows protects
it with the per-user profile's NTFS ACLs; `chmod` is not meaningful there. For
stronger protection, encrypt the system disk with BitLocker. Treat the file like
a password file either way.

**Never run the Linux and Windows copies at the same time.** The "already in
use" lock is per machine, so it cannot stop two computers from reusing the same
mesh keys at once; concurrent SEQ use can break the mesh. Close the app or CLI
on one machine before starting the other, and copy `state.json` only while the
other machine's app is closed.

### Do I need to install Python?

Yes for a source checkout. If setup cannot find a suitable Python, it prints
the commands below as well as the python.org link. Bundling CPython in the
repository is not recommended: it adds roughly 100 MB, needs its own security
updates, and a repository that ships `python.exe` is more likely to trip
antivirus rules.

If you want a user-local Python without touching the system installation,
[`uv`](https://docs.astral.sh/uv/) can install and manage it:

```powershell
winget install astral-sh.uv

# new PowerShell window, from the project folder:
uv python install 3.13
.\setup-windows.ps1 -PythonVersion 3.13
```

The setup script also looks for Python versions installed by `uv`, so a plain
`uv python install 3.15` is found automatically by `py -0p` or the uv install
directories.

To keep the runtime entirely under the app folder, point
`UV_PYTHON_INSTALL_DIR` at `.python` before installing:

```powershell
winget install astral-sh.uv

# in a new PowerShell window, from the project folder:
$env:UV_PYTHON_INSTALL_DIR = "$PWD\.python"
uv python install 3.13
uv venv --python 3.13
uv pip install -r requirements.txt
```

`.\bulbgui.cmd` and `.\bulbctl.cmd` use `.venv\Scripts\python.exe`, so they pick
this environment up without further changes. A packaged Windows build that
needs no Python at all is a planned follow-up.

Windows troubleshooting:

- `python` opens the Microsoft Store → install Python from python.org, or
  disable the Store aliases under **Settings → Apps → Advanced app settings →
  App execution aliases**.
- `No suitable 64-bit Python 3.12 or newer was found` → follow the uv commands
  it prints, install a current 64-bit Python from python.org, or pass `-Python`
  / `-PythonVersion`. The error lists every interpreter it found and why it was
  rejected. Python versions newer than this README are accepted automatically;
  PyQt6 has no 32-bit wheels. If the newest release has no PyQt6 wheel yet,
  use `-PythonVersion 3.13`.
- The app starts but finds no lamp → check **Settings → Bluetooth & devices**,
  make sure the lamp is powered and close, and disconnect any phone or vendor
  app that may be holding it.
- `Access is denied` while saving state → antivirus or the search indexer
  briefly held the file open. The app retries; add an exclusion for the state
  folder if it keeps happening.

## Desktop app (recommended)

```bash
cd bluetooth-mesh-bulbs
./bulbgui
```

It is also in the application menu as **Mesh Bulbs**, installed by
`setup-linux.sh` at `~/.local/share/applications/bulbgui.desktop`. On Windows
run `.\bulbgui.cmd` from the project folder instead (see above).

- Pick a bulb on the left; the app connects on demand and keeps the proxy
  session open, so subsequent clicks are instant.
- **Power**, **Brightness**, **Colour temperature** and ten light presets
  (plus a colour picker) on the right. Switching a bulb back on restores its
  last non-zero brightness.
- **Warm white** and **White** use the lamp's real colour-temperature channel
  (2700 K and 4000 K). The other presets send hue/saturation, and the
  temperature slider moves to the closest white point for that colour (shown as
  `≈ 1260 K`); dragging the slider switches back to white light.
- Status is polled every 10 s (this also keeps the bulb's proxy session alive)
  and after every command. If the session does drop, the app discards it and
  reconnects on the next poll or the next click.
- Everything runs as your normal user; the window never blocks while Bluetooth
  is connecting.
- While the app is running it holds a lock on the state file. Close it before
  using `bulbctl` (and vice versa); otherwise you get a clear "already using"
  error. This prevents two processes from reusing mesh SEQ numbers.
- **Controller 0x0001…** shows the mesh unicast address this computer uses.
  Give each computer its own address when they share the same bulbs; see
  **Use two computers regularly** below.

### Add a new bulb

1. Click **Add bulb**.
2. **Factory-reset the lamp**: switch it off and on **5 times in a row**
   (about 1–2 s on, 1–2 s off). It should flash or pulse when it is in pairing
   mode.
3. Keep it within a metre of the computer.
4. Press **Scan for new bulbs**, select the unprovisioned bulb in the results,
   give it a name, then **Add selected bulb**.

The app provisions the lamp into *your* mesh, binds the AppKey to every
controllable model, and adds it to the collection. It takes up to about a
minute. Telink-based lamps only accept the provisioning connection in a short
window after power-up, so start the scan right after the last power cycle.

> A lamp that is already provisioned (including one previously used with the
> vendor app) will not advertise for provisioning until it is factory-reset.

## CLI

The CLI shares the same state and the same mesh session code as the GUI.

```bash
./bulbctl devices                 # list the collection
./bulbctl scan                    # unprovisioned beacons + mesh proxies
./bulbctl provision --name Desk   # add a factory-reset lamp
./bulbctl --device Desk on
./bulbctl --device Desk level 40  # percent (lamp's own scale is 1..50)
./bulbctl --device Desk temp 2700 # Kelvin
./bulbctl --device Desk colour ff8800
./bulbctl --device Desk status
./bulbctl --device Desk dump      # composition data
./bulbctl rename --device Desk Lamp
./bulbctl remove --device Lamp    # forget it (asks first)
./bulbctl configure --device Desk # re-install AppKey + bind models
./bulbctl export --all mesh-backup.json        # keys + every bulb
./bulbctl export --device Desk desk-bulb.json  # keys + one bulb
./bulbctl import mesh-backup.json              # merge, or adopt if empty
./bulbctl import mesh-backup.json --replace    # replace this mesh
./bulbctl controller-address                   # show this computer's address
./bulbctl controller-address 0x7fff            # give it its own address
```

`--device` accepts a name or `0x0002`; omit it to use the first bulb. It works
before or after the command name. On Windows use `.\bulbctl.cmd` in place of
`./bulbctl`.

## This lamp's actual ranges

Measured from its composition data and Lightness/CTL/HSL status messages:

- **Brightness (Lightness)**: `1..50`, not `1..65535`. The GUI and CLI scale
  percentages for you.
- **Colour temperature (CTL)**: `1000..12000 K` (typical use 2700–6500 K).
- **HSL colour**: hue `0..360°`, saturation `0..100 %`, lightness shares the
  brightness scale. These are the lamp's vendor units; values are clamped if
  you send the usual SIG `0..65535` range. Verified visually: `ff0000` is red,
  `00ff00` green, `0000ff` blue (hue 0/120/240, saturation 100).
- Models: OnOff `0x1000`, Lightness `0x1300`, CTL `0x1303`, HSL `0x1307`
  (element 0), CTL Temperature `0x1306` (element 1), HSL Hue/Saturation
  `0x130A`/`0x130B` (elements 2/3).
- It ignores Generic Level SET, so brightness is driven through Lightness SET.

## State and backup

State lives in `~/.config/bulbctl/state.json` on Linux and
`%LOCALAPPDATA%\bulbctl\state.json` on Windows: NetKey, AppKey, per-bulb device
keys, unicast addresses and the SEQ cursor. On Linux the app keeps the file at
mode `0600` inside a `0700` directory; on Windows the per-user profile ACLs
apply.

**Back it up; never commit it.** It is the only way to talk to the lamps. Lose
it and each lamp must be factory-reset and provisioned again. Moving between
machines is fine — copy `state.json` while the app is closed on both — but never
let two machines control the mesh at the same time. If you switch back and
forth regularly, give each computer its own controller address instead; see
**Use two computers regularly** below.

### Move to another computer

The GUI's **Export…** button has **Whole mesh** and **Selected bulb** entries;
**Import…** loads a file. The same operations are available in the CLI:

```bash
./bulbctl export --all mesh-backup.json
./bulbctl export --device Desk desk-bulb.json
./bulbctl import mesh-backup.json
```

- A **whole-mesh** file contains the NetKey, AppKey, every device key, the
  bulb list and the SEQ cursor. Import it into an empty setup, or merge it into
  a setup with the same mesh. Choose **Replace** (GUI) or `--replace` (CLI) to
  replace the local mesh and bulb list.
- A **single-bulb** file is self-contained: it carries the mesh keys plus that
  bulb's device key, address and models. It can seed a new computer, or be
  merged into an existing copy of the same mesh.
- Importing a file from a **different mesh** into a non-empty setup is refused
  unless replacement is explicitly confirmed; two meshes cannot be combined.
  A single-bulb file cannot graft one lamp onto an unrelated existing mesh:
  replace (which adopts that bulb's mesh) or factory-reset and provision the
  lamp into the current mesh instead.
- The exported JSON contains all the keys. It is written with mode `0600` on
  Linux and inherits the user profile ACLs on Windows. Keep it private, delete
  copies you no longer need, and transfer it securely.
- After moving, keep the old controller **closed**. The per-machine lock cannot
  see the other computer, and two controllers using the same keys at once can
  break the mesh through SEQ reuse.

### Use two computers regularly (one at a time)

If you switch between two computers often, do not copy the state file on every
switch. Give each computer its own controller unicast address instead:

- Leave the first computer at `0x0001`.
- On the second computer, set a free address once, for example
  `./bulbctl controller-address 0x7fff`, or use the GUI's
  **Controller 0x0001…** button. `import --controller-address 0x7fff` does it
  in the same step as the first import.

The lamps keep replay protection per source address, so each computer now has
an independent SEQ cursor. You can close one and open the other; no export or
import is needed for ordinary control. Keep exactly **one** controller running
at a time.

Use **Merge** imports (not **Replace**) when bulbs are added, renamed or
removed: Merge preserves each computer's controller address, while Replace
copies the other computer's address and undoes the separation. The address
must be a free unicast address not used by a bulb; `0x7fff` is a good choice
for a small mesh, because provisioning allocates new bulbs upward from
`next_unicast`.

Do not try to reset SEQ to make a stale copy work. A new controller address
already starts a fresh replay entry in the lamps; an old SEQ on the same
address is ignored as a replay. When you change the address, the app advances
SEQ by a safety margin so even an address that a previous controller used
starts ahead of its old replay entry.

The vendor app can no longer control a lamp once it is on this mesh; that is
expected. To return a lamp to the vendor app, factory-reset it.

## Troubleshooting

- `Bluetooth is off or blocked` → `sudo rfkill unblock bluetooth`
- **No unprovisioned bulbs found** → factory-reset the lamp (5× off/on), keep
  it close, and scan immediately after the last cycle.
- `the lamp did not answer` → is it powered and in range? The mesh proxy advert
  is flaky, so the app retries the whole find-then-connect cycle.
- **All bulbs stop responding at once** → the controller's SEQ cursor may be
  behind what the bulbs accepted, so every command is discarded as a replay.
  This can follow a crash or force-quit. The app detects an unclean exit and
  advances SEQ automatically on the next start; if it still happens, run
  `./bulbctl controller-address` to move to a fresh source address.
- **Add bulb** fails after provisioning with a timeout → the lamp is already on
  the mesh; do not factory-reset it. Run
  `./bulbctl configure --device NAME` to retry the AppKey install and model
  binding. The add flow retries this automatically up to three times.
- `another Mesh Bulbs or bulbctl process is already using …` → only one process
  may use the mesh keys at a time. Close the GUI before running the CLI (or the
  reverse). This lock is per machine; see the Windows notes about running only
  one computer at a time.
- **Windows-specific problems** (Python not found, no lamp discovered, access
  denied when saving state) → see the Windows troubleshooting list above.
- `0x1828` advert with `node-identity` instead of `network-id` is usable but
  unverified; the app prefers a Network ID match.
- Removing a bulb deletes its device key. The lamp keeps working on the mesh but
  must be factory-reset before it can be added again.

## Development

The offline suites need no Bluetooth hardware. They create temporary mesh states
and never read your real `state.json`.

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m ruff check .
QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest -q
```

On Windows:

```powershell
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.venv\Scripts\python.exe -m ruff check .
$env:QT_QPA_PLATFORM = "offscreen"
.venv\Scripts\python.exe -m pytest -q
```

CI runs the same checks on Linux and Windows for Python 3.12 and 3.13. The
vendored `btmesh` and phase0 trees are described in `third_party/README.md`;
see `CONTRIBUTING.md` before opening a pull request.
